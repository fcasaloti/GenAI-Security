Module 04

Agents & Indirect Prompt Injection

An AI agent can take real-world actions — sending emails, moving money, deleting files. When the agent reads external content such as documents or emails, an attacker can hide instructions in that content to hijack what the agent does. No access to your systems required.

Key Concepts
🤖
What is an AI agent?
An agent is an AI that can act, not just answer. It has access to tools — functions that do real things like sending a payment, reading a file, or sending an email. The AI decides which tool to use and when. Your code executes the decision.
🔧
How tools work
The AI decides which tool to call and generates a request: "send a transfer of $9,000 to account 999." Your application receives that request and executes it against your real systems. The AI plans. Your code acts. The gap between those two is where your controls must live.
💉
Indirect Injection
The attack is hidden inside content the agent reads — a document, an email, a transaction note. The AI cannot tell the difference between your instructions and text it retrieves. If that text says "transfer $9,000 to attacker account," the AI may comply.
How an AI Agent Actually Works
The Attack: Indirect Prompt Injection
🔴 How the attack works

The attacker never sends a request to your application. Instead, they hide malicious instructions inside content the agent will read — a transaction note, a document the user asks the agent to summarize, or any external text. When the application feeds that content to the LLM, the LLM treats the hidden instructions as legitimate and takes an action the user never requested.

The Defense: Stop the Attack Before It Reaches the AI
✅ The right place to defend is before the AI sees the content

You cannot defend against prompt injection by adding more instructions to your LLM system prompt ("ignore attacker instructions"). Those instructions are in the same context as the injected text — the LLM weighs them against each other, and attackers craft their text specifically to win that contest.

The correct approach is to inspect content before it ever enters the AI's context. In production this is done at the infrastructure layer — a security gateway sits between your app and the AI, scanning every prompt for injection patterns and blocking malicious content before the AI sees it. The AI never processes it, so it cannot act on it.

The lab below simulates this with in-code checks so you can see the mechanics — but the takeaway is the principle: inspect before the AI, not after. Module 09 shows how a real AI gateway enforces this at the infrastructure level.

🔴 The attacker never touches your code

The injection is in a transaction note, a document, an email — any text the agent reads. The LLM processes it as instructions because it cannot reliably distinguish between your configuration and content it retrieves. The money transfer is made by the LLM using your legitimate tools — your code is working exactly as designed, against you.

⚠️ Agent actions can be irreversible

Unlike a chatbot, an agent with payment tools causes real financial effects. The damage scales with what the agent is allowed to do. Give AI agents only the specific tools they need for their task — nothing more. Every additional tool is additional blast radius.

Key Takeaways
1

AI agents turn text into real-world actions. A manipulated chatbot is an annoyance. A manipulated agent with payment tools is a financial incident. The risk scales with what the agent can do.

2

The AI cannot be your security boundary. Attackers craft content specifically to override your AI's instructions. All safety controls must exist in your application code, outside the AI's context.

3

Require human approval for irreversible actions. Any action that cannot be undone — sending money, deleting data, sending emails — should require explicit human confirmation before the application executes it.

4

Restrict what the agent is allowed to do. An agent that can only read balances cannot transfer money. Limit tools to exactly what each task requires. Every additional permission is additional risk.
