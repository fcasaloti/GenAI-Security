Module 07

Guardrails

Defense in depth for LLM applications. Guardrails are independent security controls that run before and after the LLM — checking inputs for injection, redacting PII, classifying intent, and scanning outputs. They don't trust the model to be safe.

Core Concepts
🔍
Pre-call (Input) Scanning
Check every input before sending to the LLM. Catches injection patterns, sensitive topics, malformed requests. Cheap to run — regex and keyword matching before any LLM call.
🔒
PII Detection & Redaction
Credit cards, SSNs, emails, phone numbers, account numbers are detected and redacted before reaching the LLM. The model never sees the raw sensitive data.
⚖️
LLM-as-Judge
A second LLM call classifies intent: benign, injection, sensitive, or off-topic. More accurate than regex but expensive — run it last, only if cheaper checks pass.
Defense-in-Depth Pipeline
✅ Defense in Depth Principle

No single layer is sufficient. The regex scanner misses creative injections. The LLM judge can be fooled. The output scanner only catches things that made it through. Together, they require an attacker to bypass all four independently — which is dramatically harder than bypassing any one.

💡 Execution Order = Cost Optimization

Run cheapest checks first. A regex scan costs ~0ms. A PII detector costs ~1ms. An LLM-as-judge costs ~800ms and $0.001. If the regex catches it, you never need the LLM call. In production with thousands of requests, this order reduces latency and cost by 60–80%.

⚠️ Why Build Your Own vs. Use Runtime Security (API)?

This home-built pipeline covers the basics but has significant gaps: no threat intelligence feed, no model drift detection, no cross-request pattern analysis, no compliance reporting. Runtime Security (API) runs as a managed guardrail layer via an AI Gateway — integrates in one config line and covers threat categories your regex will never anticipate. Module 10 shows exactly how this works in practice.

Key Takeaways
1

Guardrails run outside the LLM trust boundary. Even if the LLM is compromised or jailbroken, the guardrail layer still runs. The LLM cannot instruct a code-level scanner to stop scanning.

2

PII should never reach the model. Redact before sending. If the model never receives a credit card number, it cannot leak it — regardless of how creative the attacker is.

3

LLM-as-judge catches what rules miss. An LLM understands intent, not just pattern. "Can you help me plan a surprise party for my boss?" is benign. A regex for "boss" would be absurd. The judge understands nuance.

4

Scan outputs too. The LLM might be manipulated into generating harmful content that bypassed input filters. The output scanner is the last line of defense before the user sees anything.
