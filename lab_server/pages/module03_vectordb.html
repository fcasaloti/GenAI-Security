Module 03

Vector Database & Data Poisoning

ChromaDB stores and searches embeddings at scale. An attacker who can write a document into the database controls what context your LLM sees — without touching your application code.

Core Concepts
🗄️
Vector Database
Stores documents alongside their embedding vectors. Instead of SQL queries, you search by semantic distance — "give me the N documents closest in meaning to this query."
🎯
Nearest Neighbor Search
Vector databases like ChromaDB use HNSW (Hierarchical Navigable Small World) graphs to find the closest vectors in milliseconds, even across millions of documents. This lab uses a lightweight in-memory store with cosine distance.
☠️
Data Poisoning Attack
Inject a document that mirrors the vocabulary of likely user queries. It wins every similarity search on that topic, replacing legitimate context with attacker-controlled content.
How Documents Are Actually Stored
💡 Vector DBs store chunks, not documents

A vector database never stores a full document as one unit. Documents are first split into chunks — small overlapping pieces of text (typically 200–500 words each). Each chunk gets its own embedding vector and is stored independently. When you query, you retrieve the most relevant chunks, not the most relevant documents.

Why chunks? Because a 50-page document has hundreds of distinct topics. Embedding the whole thing produces one vector that blurs everything together — you'd never find the specific paragraph that answers the question. Chunking keeps each vector focused on a single idea.

ChromaDB Architecture + Attack Path
🔴 Write Access = Game Over

Anyone who can add documents to your vector database controls what your LLM knows. This includes: open document upload endpoints, CI/CD pipelines that ingest external content, web scrapers that add pages to a knowledge base, and any user-submitted content that gets embedded and stored.

⚠️ Low Attack Distance Wins

The poisoned document in this lab scores distance 0.12. The next legitimate document scores 0.44. The LLM only sees the top 2 results — so the legitimate document gets displaced by 4x. The attacker doesn't need a perfect match, just a better one.

💡 Defense: Document Provenance Tracking

Store the source, timestamp, and author of every embedded document. Before including retrieved chunks in a prompt, check if the source is trusted. ChromaDB metadata fields make this straightforward.

Key Takeaways
1

Vector DBs have no built-in trust model. All documents are equal. The nearest one wins, regardless of source.

2

The attack works by mirroring query vocabulary. Attackers don't need to know exact queries — they model likely user intents and optimize document text toward those.

3

Distance thresholds are a partial defense. Rejecting results above a distance cutoff reduces the attack surface but doesn't eliminate it — a well-crafted poisoned document will score below the threshold.

4

Access control on ingestion is the primary defense. Treat your vector database write path like a database write path — authenticate, authorize, and audit every insertion.
